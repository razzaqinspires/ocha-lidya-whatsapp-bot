# Owner Identity and Configuration Security

## Trust boundary

The configured `bot.owner` phone number is the source of truth. Owner verification accepts only a PN JID resolved from Baileys metadata or the trusted Baileys `lidMapping` API. It does not accept `pushName`, profile display name, message body, quoted instructions, AI history, or a caller-supplied `isOwner` flag. `fromMe` messages are not treated as inbound owner commands.

When Baileys provides both a LID and the matching PN for the configured owner, Ocha stores that pair in `data/owner-lid-map.jsonl` using mode `0600`. The file contains only owner mappings and is excluded from Git. Later messages can use this previously verified mapping if Baileys omits an alternate PN. A LID is never converted into a phone number by reading its digits. If no trustworthy mapping exists, the request fails closed and the sender is not granted owner access.

The dispatcher recalculates owner status for every message, and `authorize()` repeats the check for owner-only commands. Natural-language AI responses do not grant permissions. Commands such as `.nexora`, `.config`, `.master`, and other owner-only plugins require backend verification.

## Configuration disclosure

- A verified owner can request a non-secret configuration snapshot in a one-to-one private chat using natural language or `.config show`.
- The snapshot is generated by local code and bypasses the LLM. It is not stored in AI history.
- Sensitive property names are redacted recursively. Credential-looking strings, authorization material, PEM private keys, and embedded URL passwords are also filtered.
- Environment variables are represented only as configured/not configured. Their values are never serialized into WhatsApp messages or model prompts.
- `.env`, API keys, PATs, access/refresh tokens, passwords, WhatsApp auth/session files, private keys, database journal contents, and raw signal credentials are not disclosed through chat, including to the owner. Inspect or rotate those values directly on the VPS using a trusted local shell.
- Non-owner requests for configuration or secret material receive a deterministic backend denial. A prompt that says “I am the owner” cannot change this decision.

## Owner setup check

1. Confirm `bot.owner` in the persisted Ocha configuration is the owner's WhatsApp phone number in international digits, without `+` or punctuation. The bot's own connected phone is configured separately as `bot.expectedNumber`.
2. Send a private message from the owner WhatsApp account. Baileys must expose a PN JID, an alternate PN field, or a verified LID mapping for that message.
3. Check the debug event `Incoming sender identity verified from WhatsApp metadata`. It logs only `ownerVerified`, `senderPnResolved`, whether the source is a LID, group/private state, and `fromMe`; it does not log the full phone number.
4. Request the configuration snapshot in the private chat. If verification is unavailable, do not weaken the checks or accept a chat claim; update Baileys/session metadata and verify the configured owner number from the server.

## Operational limits

No software can guarantee that every future model or dependency is bug-free. The security boundary therefore lives in deterministic backend checks, not in the AI prompt. Keep the owner number, WhatsApp session directory, `.env`, JSONL database, and VPS shell access restricted. Do not expose Docker's API socket; access to a rootful Docker daemon is effectively host administrator access.
